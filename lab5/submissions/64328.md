## 1. Diagnoza workflow startowego `ci.yml`

### Powtarzana praca (min. 3 miejsca)
1. `actions/checkout` jest wykonywany w każdym z 7 jobów — kod pobierany jest 7 razy.
2. `actions/setup-dotnet` (instalacja .NET 8) powtarza się w 4 jobach backendu, a `actions/setup-node` w 3 jobach frontendu.
3. `dotnet restore` jest wykonywany w `backend-restore` i ponownie w `backend-build`; `dotnet test` i `dotnet publish` dodatkowo same robią restore + build od nowa.
4. `npm install` jest uruchamiany 3 razy (`frontend-install`, `frontend-test`, `frontend-build`), bez cache (`package-manager-cache: false`) i bez lockfile'a w trybie `npm ci`.

### Równoległość i zależności

- Wewnątrz łańcuchów joby czekają sekwencyjnie przez `needs`:
  - `backend-restore` → `backend-build` → `backend-test` → `backend-publish`
  - `frontend-install` → `frontend-test` → `frontend-build`

### Pytanie analityczne
Dlaczego `backend-test` znowu pobiera i buduje kod, choć wcześniejszy job już go zbudował?
Każdy job uruchamia się na **osobnym, świeżym runnerze** (osobnej maszynie wirtualnej). `needs` ustala tylko kolejność uruchamiania — nie przekazuje plików, wyników kompilacji ani zainstalowanych zależności. Dlatego każdy job musi sam zrobić checkout, zainstalować SDK i ponownie zbudować projekt. Przekazanie plików między jobami wymaga artefaktów, a przyspieszenie pobierania zależności — cache.

## 2. Zoptymalizowany workflow `ci-optimized.yml` — uzasadnienie zmian

| Zmiana | Uzasadnienie |
|---|---|
| 7 jobów → 2 joby (`backend`, `frontend`) | Checkout i instalacja SDK wykonywane raz na job zamiast w każdym kroku łańcucha. |
| Brak `needs` między `backend` i `frontend` | Oba joby działają równolegle i niezależnie. |
| `dotnet restore` raz, potem `--no-restore`, `--no-build` | Restore i build wykonywane tylko raz; test i publish używają gotowej kompilacji. |
| `--configuration Release` we wszystkich poleceniach .NET | Spójna konfiguracja — `--no-build` działa tylko, gdy test/publish szukają wyników tej samej konfiguracji. |
| Restore/build projektu testowego | Projekt testowy referuje `ProductApi`, więc jedno polecenie obejmuje oba projekty. |
| `npm ci` zamiast `npm install` | Instalacja dokładnie wg `package-lock.json`, powtarzalna i szybsza w CI. |
| `actions/cache@v6` dla `~/.nuget/packages` (klucz: OS + hash `.csproj`) | Pakiety NuGet nie są pobierane od nowa, dopóki nie zmienią się zależności. |
| `setup-node` z `cache: npm`, `package-manager-cache: true`, `cache-dependency-path` | Cache pobranych paczek npm (nie `node_modules`, więc `npm ci` dalej jest potrzebne). |
| `upload-artifact` dla `backend-publish` i `frontend-dist` | Wynik konkretnego przebiegu dostępny do pobrania. |
| `permissions: contents: read`, `paths`, `concurrency` | Minimalne uprawnienia; workflow uruchamia się tylko dla zmian w lab5; nowy commit anuluje starszy przebieg w tym samym PR. |

### Jak wymagany check blokuje merge
Jeśli prowadzący w regułach repozytorium (branch protection / ruleset dla `main`) ustawi dany check jako **required status check**, przycisk *Merge* w PR jest zablokowany, dopóki ten check nie zakończy się sukcesem na ostatnim commicie PR. Czerwony check = brak możliwości scalenia; po wypchnięciu poprawki i zielonym wyniku merge staje się możliwy.
